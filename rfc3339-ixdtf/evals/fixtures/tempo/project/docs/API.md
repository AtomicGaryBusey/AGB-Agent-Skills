# Tempo Events API

Tempo is the scheduling backend for team calendars. This page describes the
`GET /v1/events` response and the timestamp contract every client relies on.

## Response shape

```json
{ "events": [ { "id": "evt_0001", "title": "Quarterly planning", "start": "…", "…": "…" } ] }
```

Each element conforms to [`schema/event.schema.json`](../schema/event.schema.json).
The schema is the source of truth: every response is validated against it in
CI, which guarantees that all timestamp fields are well-formed before they
reach clients.

## Timestamp contract

All timestamps are ISO 8601 strings. Clients should accept any ISO 8601
representation the server emits, for example `2026-03-14T09:30:00-04:00`,
`2026-03-14T13:30:00Z`, or the compact form `20260314T133000Z`.

| Field            | Meaning                                                                                     |
|------------------|---------------------------------------------------------------------------------------------|
| `start`          | Event start, IXDTF (RFC 9557): local date-time, numeric offset, `[Area/City]` zone, optional `[u-ca=…]`. |
| `start_utc`      | The same instant as `start`, expressed in UTC. Used for sorting.                            |
| `end`            | Event end, RFC 3339 date-time with the venue's numeric UTC offset.                          |
| `reminder_at`    | When the reminder fires, RFC 3339 date-time with offset.                                    |
| `created_at`     | When the event was created, RFC 3339 date-time with offset.                                 |
| `received_at`    | Server receipt time, UTC instant.                                                           |
| `all_day_date`   | Present only for all-day events: the calendar date.                                         |
| `source_seen_at` | Partner-feed events only: the instant the partner last saw the event. Partners report a bare POSIX time, so the local offset is unknown. |

### Precision profile

Instants generated by Tempo (`received_at`) carry exactly three fractional
digits (millisecond precision) and use `Z`, e.g. `2026-09-24T12:00:00.123Z`.
Clients must still accept any number of fractional digits, since partner
data passes through unchanged in other endpoints.

### Case

Generators use upper-case `T` and `Z`. Parsers accept lower-case `t` and `z`
as RFC 3339 §5.6 allows.

### Suffix handling (RFC 9557)

* The time-zone suffix, when present, comes first.
* Unknown elective tags (`[key=value]`) are ignored.
* A tag marked critical (`[!…]`) that the client cannot process makes the
  whole timestamp invalid.
* If a key appears more than once, the first occurrence is used.
* A critical time zone whose rules disagree with the numeric offset is an
  error; with `Z` there is no disagreement to check.

## Partner feed ingest

Partner feeds send `start` / `end` as IXDTF strings. Records are parsed with
`timeutil.parse_ixdtf` and re-emitted using the contract above.
