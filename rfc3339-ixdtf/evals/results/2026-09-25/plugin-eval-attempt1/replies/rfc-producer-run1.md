# RFC 3339 / RFC 9557 audit of Tempo's timestamp producers

**Scope:** I reviewed the producers only: the `format_*` helpers in `timeutil.py` and every timestamp field that `serialize()` emits in `api.py`. `docs/API.md` and `schema/event.schema.json` are covered only where they make claims about those fields. The consumer code (`parse_timestamp`, `parse_ixdtf`, `client/parse.mjs`) was not audited.

**Profiles:**
- `start` claims IXDTF (RFC 9557).
- `end`, `reminder_at` and `created_at` claim RFC 3339 date-time (`docs/API.md:27-29`).
- `received_at` has a stated profile: exactly 3 fractional digits and `Z` (`docs/API.md:36-37`).
- Producers are declared to emit upper-case `T`/`Z` (`docs/API.md:43`).

**How this was checked:** by reading the code only. There was no shell, so I did not run `rfcdt.py scan`, the conformance vectors, or `api.py`. Every output string below is worked out by hand from the code and the sample data in `api.py:61-103`. I couldn't open the skill's `check-index.md` (permission denied), so findings cite RFC sections instead of check IDs.

**Summary:** 8 nonconformities, 3 deviations, 3 advisories, 1 interpretation note.

Across all five sample events, 17 of the 32 emitted timestamp strings are outside the RFC 3339 grammar (every `end`, `reminder_at` and `created_at`, plus the `start` of `evt_0002`). Another 5 are grammatical but give the wrong instant (every `start_utc`).

**Producers with no issues found:**
- `format_instant` (`timeutil.py:41-46`, `received_at` at `api.py:37`): it rejects naive input, converts to UTC, emits 3 fractional digits and upper-case `Z`, and matches the stated profile. For example, the test vector `2026-03-14T13:30:05.987Z` (`tests/test_timeutil.py:17`) is valid.
- `format_ixdtf` for `ZoneInfo`-backed datetimes: for example, `2026-09-11T19:00:00-07:00[America/Los_Angeles][u-ca=hebrew]` is valid IXDTF.
- Every producer emits upper-case `T` and `Z`.

## Interpretation notes
- **`reminder_at` arithmetic across DST (`api.py:35`).** `event.start - event.reminder` on a `ZoneInfo` datetime subtracts wall-clock time. Near a DST transition that can give a nonexistent or shifted local time, i.e. a wrong instant. For example, an event at 2026-03-08 03:10 EDT gives 02:55 with offset −05:00, which is 07:55Z instead of the correct 06:55Z. This is a time-zone arithmetic bug, not a serialization one, so it's outside the RFC grading. I'm flagging it because the string it produces would label a wrong instant. Fix: subtract in UTC and then call `astimezone(tz)`.
