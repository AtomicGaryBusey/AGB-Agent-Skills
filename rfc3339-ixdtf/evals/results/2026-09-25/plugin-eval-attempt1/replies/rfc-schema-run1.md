# RFC 3339 / RFC 9557 adherence audit: Tempo timestamp contract

**Scope:** I reviewed the **schema** (`schema/event.schema.json`) and the contract docs (`docs/API.md`). The `start` field uses the **IXDTF** profile and every other field uses **RFC 3339**. The contract declares these options: upper-case `T`/`Z` for generated output (API.md:43); `received_at` always has 3 fractional digits and `Z` (API.md:36-37); clients accept any fractional precision (API.md:38); elective tags are ignored, critical ones enforced, and the first duplicate wins (API.md:48-54). It states nothing about leap seconds, the space separator, the tz database, experimental keys or which `full-date` production to use.

**Evidence:** This is a static review only. No shell was available, so I did not run the `rfcdt.py scan`, the conformance vectors, `rfcdt.py check` or `api.py`. To test the "CI guarantees well-formed" claim, I worked out producer output by hand from `api.py` and `timeutil.py`. Of the 9 fields, 5 would produce invalid or wrong-instant output (rows 1 and 3). I also could not open the skill's `references/check-index.md` (Grep permission denied), so the check IDs below are descriptive labels rather than catalog IDs.

**Summary:** 4 nonconformities, 3 deviations, 7 advisories, 2 interpretation notes.

## Interpretation notes (readings I used)
- **9557 §4.1 `time-zone` precedence:** I read it as `"[" critical-flag (time-zone-name / time-numoffset) "]"` when judging whether `[UTC+05:30]` is invalid (row 3). It fails under either reading, because `:` is not a `time-zone-char` and `UTC+05:30` doesn't match `time-numoffset`.
- **`start_utc` using `Z` rather than `+00:00`:** The local offset is known (it's carried in `start`), so under 9557 §2 you could argue for either. I did not grade that choice. I only graded the wrong instant (row 2) and the unenforced profile (row 9).
