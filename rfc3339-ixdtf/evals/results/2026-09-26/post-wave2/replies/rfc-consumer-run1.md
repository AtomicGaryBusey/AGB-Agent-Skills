# RFC 3339 / RFC 9557 audit: Tempo timestamp consumers

**Scope:** I audited only the consumers: `timeutil.parse_timestamp` (RFC 3339), `timeutil.parse_ixdtf` (IXDTF, used by partner-feed ingest in `api.ingest`) and `client/parse.mjs` `parseTimestamp`/`parseSuffix` (IXDTF). The contract in `docs/API.md` sets these options: lower-case `t`/`z` accepted (`docs/API.md:43-44`), any number of fraction digits (`docs/API.md:38-39`), unknown elective tags ignored (`:49`), first duplicate wins (`:52`). It states no leap-second policy and no space separator.

**Evidence:** Static review only. No shell was available, so I did not run the scanner, the conformance vectors, `selfcheck` or `tests/test_timeutil.py`. Every "input → result" below comes from reading the code, not from running it.

**Summary:** 12 nonconformities, 1 deviation, 2 advisories, 5 review notes.

## Review notes
- **Sub-minute (LMT) zone offsets** (`timeutil.py:147`, `client/parse.mjs:59,90`): the consistency check compares exact offsets. Before a zone adopted standard time its offset often had seconds (for example Paris before 1911 was +00:09:21), which `time-numoffset` cannot express. So any historical timestamp with a critical zone is always rejected. RFC 9557 leaves this open. Rounding to the nearest minute is a reasonable tolerance.
- **Leap-second representation** in JS (`client/parse.mjs:77,99`): mapping `:60` to `:59` and setting `leapSecond` is an acceptable choice once #10 is fixed. For the month rule I would use the Appendix D reading (end of March, June, September or December from 1972), or the real IERS table.
- **Temporal dependency** (`client/parse.mjs:58`): this needs a global `Temporal`. Without it, the `catch` at line 85 rejects every critical zone and silently drops elective ones. That is conformant (the zone cannot be evaluated), but it quietly degrades behaviour, so check the target runtimes.
- **Handled correctly:** `Z`/`-00:00` with a critical zone skips the consistency check (`timeutil.py:145`, `client/parse.mjs:89`). Unknown elective zones are dropped and unknown critical zones rejected. The zone is required to come first. Experimental `_` keys are rejected (`client/parse.mjs:49`; Python rejects them through its allowlist). Offset ranges are checked. Fractions are truncated to µs/ms. Python validates impossible dates. Python's first-wins for elective duplicates is right (`timeutil.py:135`).
- **Tz-name grammar:** neither parser checks it directly. They rely on `ZoneInfo` or Temporal to reject bad names. Note that `ZoneInfo` lookups follow the filesystem, so on case-insensitive filesystems like macOS they may accept wrong-case names.

## Not run / not applicable
- `rfcdt.py scan`, `run_vectors.py` (310 vectors), `rfcdt.py selfcheck` and the unit tests were not run because no shell was available. None of the vector buckets are graded from tool output, and I make no clean-result claims.
- **Out of scope (producers and schema), not graded, but worth a follow-up:**
  - `format_utc` (`timeutil.py:51`, used at `api.py:33`) labels the local wall time with `Z`, which gives the wrong instant.
  - `%z` gives `-0400` with no colon (`timeutil.py:13,56`).
  - `format_reminder` drops the seconds (`timeutil.py:61`, and the test at `tests/test_timeutil.py:32` asserts that).
  - `created_at` is naive, so it has no offset (`api.py:25,36`).
  - `all_day_date` is a date but the schema says `format: date-time` (`schema/event.schema.json:50`).
  - `format_epoch` emits `+00:00` for an unknown offset (`timeutil.py:66`).
  - `zone_label` produces `[UTC+05:30]` for fixed offsets (`timeutil.py:70`).
  - The `start` pattern in the schema is `\[.+\]` (`schema/event.schema.json:21`).
  - Given all of the above, the "CI guarantees well-formed" claim in `docs/API.md:13-15` is false.

## Assumptions
- `parse_ixdtf` is treated as an input gate because it handles partner-feed ingest (`timeutil.py:3-4`, `docs/API.md:58-59`), and `parse_timestamp` because it claims RFC 3339. That is why leniency is graded as a Nonconformity.
- The only supported calendar is `u-ca` (`KNOWN_SUFFIX_KEYS` and `KNOWN_KEYS`).
- The system tz database is available to `zoneinfo`, and Temporal is available to the client.
